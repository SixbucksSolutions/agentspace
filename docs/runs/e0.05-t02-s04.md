## What went wrong

### The root disk filled, and the sampler died with it

- **The box's root disk, 6.8G, filled between 2:29am and 2:33am,** while five cargo `target` folders
  held about 370 MB. The rest of the disk was already in use. A five-story Rust turn does not fit a
  6.8G root disk. This is a sizing fact for v0.09 (#0049) and for a project host that builds Rust
  (v0.07, #0047).
- **The record holds no disk field.** The disk's times and sizes come from the architect's notes
  and PR #52's body, and are marked A and P in the timeline.
- **The sampler wrote its record to `~/agentspace-samples` on that same disk,** so the full disk
  stopped it. At 2:33:12am its next write failed: it had written seq 208's host line and part of
  that sample's session line. It died with no end line, and its error file, on the full disk, stayed
  empty. Nothing said so until `stop` at 2:58am. This is #0109, whose fix is before v0.09's
  measurement.
- **A watcher on the sampler's liveness would have caught it,** and AGENTS.md, "Watching a
  measurement", now requires one.

### The targets moved to RAM

- **At 2:33am the dev lead moved each worktree's `target` folder to tmpfs under `/tmp`** and
  symlinked it back. The tmpfs holds its files in RAM.
- **From then, the build output counts as shared memory in the host's memory, and in no session's
  PSS.** The kernel owns those pages, and no process of the session maps them as its own. The host
  figure is "total less available" (footprint.md, "The host"), so tmpfs pages move it, and a
  session's PSS does not.
- **This record cannot show it.** It ends at 2:33:12am, within about a minute of the move at
  2:33am, and its host memory then reads 1.26 GiB. The effect on the host's memory is read from how
  the figure is made, not from a sample of it.
- **The host memory figures below are therefore the memory of the processes, before the build
  output reached RAM.** They MUST NOT size a host that builds Rust.

### The tmpfs filled too, and build output passed 5 GB

- **The tmpfs, 7.7G, filled shortly before 2:53am,** during S03's rebuild, when a link failed with
  "No space left on device". The 7.7G is about half the box's memory (15.27 GiB), which is a
  tmpfs's default size.
- **S03's `target` folder had reached 2.7 GB over its lock changes, and the reviewers' scratch
  builds held another 2.7 GB.** That is 5.4 GB in S03's `target` folder and the reviewers' scratch
  build folders, and the tmpfs was full at 7.7G. The dev lead cleared finished work, which left 588 MB used.
- **So the build output of one five-story Rust turn passed 5 GB at its peak,** and the tmpfs's
  7.7G was full. This is a sizing fact for a project host that builds Rust (v0.07, #0047), set
  beside the memory figures: a turn's build output is not in them, and a RAM-backed `/tmp` takes
  half of a 15.27 GiB box. The sources are the architect's note on card #0102 and PR #52's body.
  Whether the rest of the full 7.7G was build output is not recorded, so 5.4 GB is a floor for the
  output and the 7.7G is the ceiling the tmpfs allows.
- **PR #52's note says a jsonschema build is large,** and that S03's target folder grew over
  several re-locks.

## The host against the sessions: the gap check for #0082

#0082's trigger (card #0082) compares host CPU with the sum of every session's own and tool-call
CPU, plus the box's idle baseline, while a session is alive. It trips if the host exceeds that sum
by 0.25 cores or more sustained over a minute, or by 10% or more of the sessions' tool-call CPU over
the whole run.

- **The window is the session's: 2:27:16am to 2:33:10am, 354 seconds,** the samples seq 30 to 207.
  This is 354 seconds of a 31-minute turn, so the check covers the first compile burst and nothing
  after it.
- **The baseline is v0.04-T01's,** the architect's choice there: the box idle with the sampler's
  own CPU taken out, 0.00065 cores (docs/runs/e0.03-t02-s01.md). It lacked a desktop-app

- **A second baseline gives the same answer.** The record's own first 56 seconds, before the
