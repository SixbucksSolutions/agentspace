### The opening check failed: the default match missed the desktop-app session

- **Done-when's first line failed.** At 6:14am t01b had no session rows, while the dev lead had
  run since 6:13:31am. Its process was:

  ```
  /home/ubuntu/.claude/remote/ccd-cli/2.1.325-697a82e23a44 --output-format stream-json --verbose --input-format stream-json --effort=high --model=claude-opus-5-5 ...
  ```

  Its parent was the app's bridge, `/home/ubuntu/.claude/remote/srv/<hash>/server --serve`, whose
  parent is PID 1, and a second bridge, `server --bridge`, hung off an `sshd-session`. **This is
  D33's known gap in a new form:** a desktop-app session's argv[0] is
  `~/.claude/remote/ccd-cli/<version>`, which the default, `^(?:\S*/)?claude(?:\s|$)`, does not
  match.
- **The fix, on this story's branch:** the default becomes
  `^(?:\S*/)?(?:claude|ccd-cli/[^/\s]+)(?:\s|$)`, with a test against this exact command line, and
  the README's "Measure a turn" says so. Over every live process on the box at 6:15am it matched
  only the dev lead, in a check whose output is not committed. It reaches the box when the architect syncs it after this story merges.
- **The run went on with the regex as `--match`, not with a sync mid-run** (the architect's call):
  t01b was stopped at 6:16:26am, and t01c started at 6:16:28am with that `--match`. Its first four
  samples each held exactly one session row, `2476-254370`, and the bridge was not a session.

### What this means for the footprint

- **A desktop-app session carries a connection overhead of its own:** about 6.4 CPU-s in 2172 s,
  0.003 cores, and up to 161 MiB RSS, in two SSM session workers, the app's bridge and four
  `sshd` processes, none of them in the session's row. v0.03-T03's table SHOULD carry it as its own
  line, "connection overhead per desktop-app session". A session over plain `ssh` was not
  measured here.
- **A measurer's own polling is load.** The observer cost about as much as the connection, and it
  is the measurement's cost, not the turn's. Its 1-second poll loop forked twice a second. A later
  observer SHOULD sleep to its next snapshot in one call.

### A calibration flaw in the tripwire

- **Its baseline, t01, had neither a desktop-app connection nor an observer running.** It holds
  only the box's daemons, the keeper's holder and the sampler. So the check could not tell the
  connection and the observer from orphaned work, and both landed in the gap. A later run SHOULD
  take its baseline with the measured session's connection open and the observer running, but
  idle.
- **Against t01b's baseline instead** (0.0047 cores, which includes the box's boot aftermath, the
  desktop app connecting from 6:12am and a 2-second test run at 6:15am), the gap would be about
  10.8 CPU-seconds.
