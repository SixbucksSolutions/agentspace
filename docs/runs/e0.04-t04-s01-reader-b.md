## 1. How I would build a drop-in

### 1.1 The lease CLI (`docs/lease-api.md`, `schemas/`, `docs/state.md`, `docs/driver.md`)

**One Rust binary, `agentspace.exe`, for Windows.** Modules, in build order:

1. **`args`:** the left-to-right tokenizer of lease-api.md "Command lines": command and subcommand
   matched as ASCII letters without case, `--name[=value]` flags, the next-argument value rule,
   `-h` and `--help` in any position, positionals, and the five-step "which error is reported"
   order. Output is one of: help for a level, a usage error (with or without `field`), or a parsed
   command. Arguments are taken from the OS as UTF-16 and never re-split.
2. **`help`:** the seven help blocks as byte-exact constants with LF endings, copied from
   lease-api.md "Commands".
3. **`values`:** one normalizer per value (lease ID, project, platform, profile, size, TTL in both
   forms, state filter), each trimming Unicode `White_Space`, matching the whole value, and
   returning the normalized form, `invalid_value` or `out_of_range`. TTL arithmetic is checked for
   overflow, which is `out_of_range`.
4. **`output`:** the lease, list and error documents as compact JSON plus one LF, members in the
   documented order, absent fields left out, control characters in quoted values written `\uXXXX`,
   and the message templates of lease-api.md "Messages". Every document is validated before it is
   printed.
5. **`paths` and `clock`:** the home folder from `USERPROFILE` only, `<state folder>` and
   `<ssh folder>` from their variables, relative values made full; UTC now truncated to the second.
6. **`state`:** `leases.json` read (BOM and whitespace tolerated, shared read, write and delete),
   validated against `schemas/state/leases.state.schema.json`, derived `expired`, and replaced
   atomically through `leases.json.<hex>.tmp`; `leases.lock` opened with share mode 0, retried for
   30 seconds, then the "busy" `internal`. The schema patterns use lookarounds (`$(?!\n)`,
   `(?=[0-9])`), so the validator needs a regex engine that has them, or hand-written checks.
7. **`driver`:** a trait with place, renew and release, and one implementation named `ec2`
   (driver.md "The operations"). It holds:
   - **Support decision:** exact match on `linux/arm64`, `agent-linux`, `m`, and the three reason
     messages.
   - **CA check (state.md "Its checks"):** both files, owner-only folder and key by SID and DACL,
     the key loads unencrypted, the public key's two words equal the derived ones. Never creates.
   - **Credential:** an ed25519 key pair and an OpenSSH user certificate built in-process (serial
     0, key ID the lease ID, one principal, valid-after 5 minutes back, valid-before issue time
     plus TTL, extensions `permit-port-forwarding` and `permit-pty` only).
   - **Alias:** the `Include` line step (byte rules, backup, `ReplaceFile`), then the alias file
     written through `<ssh folder>\<alias>.agentspace-tmp-<hex>`, with the owner-mark rules.
   - **Renew:** state.md "Renewal" steps 1 to 8, with `renew-<hex>-previous-cert.pub`.
   - **Release:** owner-mark check, record first, then the alias file, then the lease folder.
8. **`commands`:** `create`, `get`, `renew`, `release`, `list`, each taking the lock (the three
   that change) before it reads, and following driver.md "What the CLI does, in order".

**What I would check it against, in this order:**
- `conformance/schemas/test-schemas.ps1` (the package itself), then `test-help.ps1`,
  `test-usage-errors.ps1` and `test-values.ps1` after modules 1 to 4, which need no state.
- `test-create-get.ps1`, `test-list.ps1` and `test-lease-driver-outcomes.ps1` after 5 to 8.
- `test-lease-certificate.ps1`, `test-lease-alias-file.ps1`, `test-lease-cmd-renew-release.ps1`
  and `test-lease-concurrency.ps1` for the credential, the alias and the lock.
- Every `test-unmet-*.ps1` in `conformance/lease-cli/`, which a rewrite MUST pass.
- Every printed document against `lease.output`, `lease-list.output` and `error.output` schemas,
  and every sample under `schemas/samples/`.

**Where I would be guessing:** the default ProxyCommand (B-01), the instance-ID cache (B-02), the
key's access rules (B-10), what a failed `create` may leave in the ssh folder (B-11).

### 1.2 The operator (`docs/operator.md`)

**A second binary for the commands, and a third for the ProxyCommand** (B-03 says why not one).
Modules, in build order:

1. **`args` and `help`:** `<command> [-GiB n] [-Alias a] [-Quiet]`, names without case, help
   first, then the `-Alias` checks with the two fixed messages, before anything is started.
2. **`messages`:** stderr only, the `agentspace: ` prefix for failures and warnings, `-Quiet`,
   exit 0 or 1 and nothing else.
3. **`programs`:** the fixed paths of "Programs it starts", the four seam variables read at the
   moment of use, the "cannot be run" failure, removal of every `*_POSIX_FD_STATE` variable,
   `AGENTSPACE_NESTED=1` for every child, and stdin wiring (a pipe, or closed).
4. **`ca`:** steps 1 to 6 of "ca", sharing the CA check with the lease CLI as one library crate, so
   the two can never disagree.
5. **`aws`:** one function per call in "Calls by command", `--region us-west-2`, `--output json`,
   the sign-in test, and the instance-ID cache at `%USERPROFILE%\.agentspace\instance-id`.
6. **`start_wait`:** "Starting the box and waiting for it": the state switch, the 20-minute
   launch-time rule, the 15-minute wait with 5-second checks, the patch question through
   `send-command` and up to 20 one-second polls, and messages printed once per phase.
7. **`push`:** the receipt and `bot.xml` (B-22), the zone (Windows ID to IANA, seven legacy names,
   the check), the stamp, the one ssh with `-o ClearAllForwardings=yes -o BatchMode=yes <alias>
   <remote command>`, the 20-second clock with a kill of the ssh's tree, the 10-second stdout
   wait, the hash line and zone line checks, and fixed warnings only. The remote command is my own
   POSIX shell text for "What the box does", steps 1 to 8.
8. **`up`, `down`, `status`, `grow`, `sync`, `deploy`:** each as its numbered steps.
9. **`proxy`:** refuse a second argument, put the two folders on `PATH`, run `up` with its stdout
   on stderr, repair the console mode, read the cache, run the tunnel with the proxy's own stdin
   and stdout, exit with its code, and print no backend text unless `AGENTSPACE_DIAGNOSTIC` is set.

**What I would check it against:**
- `conformance/operator/test-alias-refusals.ps1` and `test-proxy-arguments.ps1` after 1 to 3.
- The lease CLI harness itself, which runs `ca -Quiet` for every throwaway home, after 4.
- `conformance/operator/test-unmet-proxy-connect-time.ps1` after 5, 6 and 9.
- **Nothing in the export covers 7 and 8.** I would write my own checks from operator.md "How a
  test uses it, from outside", with stand-ins for `aws`, `ssh` and `scp` (B-51).

**Where I would be guessing:** where a compiled operator finds its checkout (B-21), the format of
`bot.xml` (B-22), the ssh and scp argument lists of `sync` and `grow` (B-23), every message the
ProxyCommand prints in place of `up`'s (B-24, B-25), and usage-error texts (B-27).

### 1.3 The keeper (`docs/keeper.md`)

**A fourth binary, Windows only.** Modules, in build order:

1. **`args`:** the argument table, the six ordered usage checks, the three stderr lines, exit 2.
2. **`log`:** one append per line that lands whole, the same line on stdout, the pass line and
   keeper line grammars, `_` for whitespace in values, reason cleaning, five tries 50 ms apart.
3. **`locks`:** `board-holder.lock` (share nothing, 100 ms retries for 10 seconds, `skipped`) and
   `board-holder-keeper.lock` (share read, one try, the PID content, `another keeper is running`).
   Neither handle is inheritable.
4. **`leases`:** the lease state reader shared with the lease CLI, without the lease lock; ready
   means stored `ready` and `expires_at` strictly after the pass time; the choice of lease.
5. **`process`:** open by PID with query and wait rights, creation time to the millisecond in UTC,
   command line read-back, parent-PID tree walk with per-handle checks, terminate leaves first,
   2-second waits, 5 rounds.
6. **`matcher`:** the `CommandLineToArgvW` splitter, rules 1 to 5, and the self-check table run at
   the start of every pass.
7. **`record`:** `board-holder.json` read tolerantly, written strictly and atomically.
8. **`start`:** the checks of "Before the start", then the handshake as written: the request, a
   launcher created through WMI's `Win32_Process.Create` (the keeper's own exe in a hidden
   launcher mode), the create-new claim, the result, the 30, 35 and 60-second bounds, the
   withdrawal, the one-shot liveness check, removal of the three files, then the record.
9. **`pass`:** "The order of a pass" steps 1 to 8, with rotation of `board-holder-ssh.log`.
10. **`watch`:** the look, tracking and proof, the fast-failure count, backoff, release grace,
    card #0068's rule, the interval floor on every path, `-MaxPasses`.
11. **`install`:** the scheduled task and its uninstall (B-43).

**What I would check it against:**
- `conformance/keeper/test-keeper.ps1` (42 cases: 21 one-pass, 20 `-Watch`, 1 for the files
  against `schemas/state/`), with `-SelfCheck`.
- `conformance/keeper/test-unmet-holder-dies-mid-pass.ps1`, which a rewrite MUST pass.
- The three `schemas/state/board-holder*.schema.json` files for every JSON file written.
- Card #0066's bar: five passes in a row beside two other copies of the suite.

**Where I would be guessing:** whether the launch files are required (B-37), the action word of
card #0068's line (B-38), the bound on a create call (B-39), the clock across a laptop sleep
(B-40), and nearly all of the installed task for a compiled keeper (B-43).
