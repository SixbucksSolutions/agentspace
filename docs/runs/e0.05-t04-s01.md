## The harness's isolation

**Terry, 2026-11-19: "isolation is enough".** No file of Terry's real `.agentspace`, `.ssh`, CA or
localswim folder was listed, read or hashed, before or after the run. What protects them is the
harness, and this is what was checked of it, by reading `conformance/lease-cli/*.ps1`.

- **The search:** every file of that folder, for `Remove-Item`, `Set-Content`, `Add-Content`,
  `Out-File`, `[IO.File]::` and `[IO.Directory]::` calls, `New-Item`, `Copy-Item`, `Move-Item`,
  `Rename-Item`, `Clear-Content`, `Set-Acl`, `icacls`, `FileStream`, `StreamWriter`, redirections and
  `.Delete(`. **The search was shown to find something first**: it returned
  `lease-check-support.ps1` line 226, a `Remove-Item` known to be there.
- **Every write and delete goes through `Assert-ConformancePath`**, at the call or in the same
  function, on the variable the call then uses, except the harness's own writes below, and with
  the one staleness below it. The reads
  (`[IO.File]::ReadAll*`, `Test-Path`) write nothing. Six files hold no write at all and no
  assertion: `test-help.ps1`, `test-lease-certificate.ps1`, `test-list.ps1`,
  `test-usage-errors.ps1`, `test-values.ps1` and `test-unmet-argument-line-feed.ps1`.
- **Where the assertion is at the variable's assignment and not at the call**, so that
  [conformance.md's "at the call"](../conformance.md#the-program-under-test-is-untrusted) is met by
  the function and not by the line: `test-unmet-release-released.ps1` (the `New-Item` and four
  `Copy-Item`s of its copies, from `$backup`, `$folderCopy`, `$aliasCopy`, `$folder`, `$aliasFile`),
  `test-unmet-failed-create-cleanup.ps1` (the `$probe` folder and its two `Remove-Item`s),
  `test-unmet-internal-no-path.ps1` (the first `Remove-Item` of `$key`),
  `test-unmet-no-ca.ps1` (`Remove-UnmetCa`), `test-lease-concurrency.ps1` (the two
  `FileStream` opens of `leases.lock`, with `OpenOrCreate`), and `lease-check-support.ps1`
  (`Reset-CcSshDir`'s `New-Item`). Each variable is assigned from `Assert-ConformancePath` earlier
  in the same function. **In every file but one, no program runs between that assertion and the
  write**, so the reparse-point check is as fresh at the write as it was at the assertion.
- **The one file where it is not, and it is a defect in the check:**
  `test-unmet-release-released.ps1` asserts `$folder` and `$aliasFile` at lines 85 and 86, runs the
  program under test's `release` at line 98, and then `Copy-Item` writes back into those two paths
  at lines 107 and 108. The program ran in between, so the reparse-point check made at lines 85 and
  86 is stale at the copy, and [conformance.md's rule is "at the call"](../conformance.md#the-program-under-test-is-untrusted).
  **The check is not changed in this story.** The architect cards the defect (#0110), and the run's
  result stands, since the build under test is not hostile.
- **Writes that do not go through it, all the harness's own on a folder it has just named, which
  [conformance.md](../conformance.md#the-program-under-test-is-untrusted) does not name as an
  exception** (the architect cards that too, #0110):
  `New-ConformanceHome` makes its four folders with `New-Item` (`harness.ps1` lines 203 to 206), and
  deletes its own `$root` in its `catch` with `Remove-Item` (line 210). They are made before the root
  exists. `$root` is `%TEMP%` and a fresh `agentspace-conformance-<12 hex>` name, built in that
  function, and no path from a program reaches either. `Assert-ConformancePath` cannot guard them, since the root does not exist yet and
  is what it measures against. `Remove-ConformanceHome` refuses any folder that is not such a name
  directly under `%TEMP%`.
- **No check was changed.**

## Every fix

**The conformance suite found nothing to fix in the program**: the build passed every file on its
first run. These are what changed, and why.

1. **The EC2 driver is registered** (`crates/agentspace-cli/src/commands/mod.rs`, `drivers()`;
   `agentspace-cli` depends on `agentspace-driver-ec2`). It returned an empty list, so `create`
   failed with "No lease driver is available". It meets
   [driver.md, The EC2 driver](../driver.md#the-ec2-driver) and
   [lease-api.md, Commands](../lease-api.md#commands). **The test is
   `commands::tests::the_build_holds_the_ec2_driver`**, which fails with an empty list.
2. **The CLI's own integration tests no longer assume there is no driver**
   (`crates/agentspace-cli/tests`). With the driver registered, their runs of the binary changed
   in two ways, and the suite caught both: a `create` in a home with no CA now fails with the
   no-CA message ([lease-api.md, Messages](../lease-api.md#messages)), and an unsatisfiable
   `create` records a lease, which a later run in the same home then listed.
   - **Each run of the binary gets a home of its own**, removed after the run (`command` and
     `run_command` in `tests/common/mod.rs`), under the temp folder, so no run sees another's
     leases. Before, all of them shared one folder.
   - **The expected message is the no-CA one** (`MSG_NO_CA`), in `output.rs` and for `create` in
     `tests/common/mod.rs`, and the in-process helper holds the EC2 driver, so that it and the
     binary still agree line for line (`usage_errors.rs`).
   - **These hold:** `output::an_internal_error_carries_only_a_code_and_a_message`,
     `output::the_subcommand_in_an_internal_message_is_lowercase`,
     `usage_errors::every_subcommand_with_a_valid_line_gets_its_commands_answer`,
     `usage_errors::a_command_subcommand_and_flag_match_without_regard_to_ascii_case` and
     `usage_errors::a_valid_line_never_prints_help_and_a_failed_one_prints_nothing_on_stdout`. Each
     failed before the change. `isolation_guard` passes too: it runs the whole suite again with the
     home moved away, and nothing created that home.
