# E0.06-T05-S02 run record: the fix for `deploy`'s hang, and a live no-op `deploy`

RFC 2119 keywords; the capitals are load-bearing.

The evidence for story E0.06-T05-S02 (card #0140, epic #0055, D42), which fixes defect #0139: the
Rust `agentspace-operator deploy` never returned after the AWS CLI's `cloudformation deploy`
([e0.06-t05-s01.md](e0.06-t05-s01.md), step D, finding 1). The sections below give the cause, the
evidence for it, the fix, its tests, and two live no-op `deploy` runs of a build of the fix against
the real stack.

**The headline: the live `deploy` returned and exited 0.** The first run (1:49am) passed the AWS
CLI's lines through, found no changes, ran `sync` to its end, and wrote the push's stamp, in about
2 minutes 20 seconds, but its exit code was not captured. **The second run (1:58am), through a
wrapper that records the code, exited 0** after 1 minute 40 seconds, with the same output, the same
`sync` install lines and the push confirmed. The box was stopped at the end of each.

  files named below.
- **This record MUST NOT carry the account ID, the instance ID, a host name, the computer name, the
  Windows user name, the stack's parameter values, a lease's ID or alias, or a token.** The box is
  written `<box>`, a path under the profile is written `%USERPROFILE%\...`, and the CA's

## The cause

**As stated by the investigator, not a guess** (line numbers as of `4f18b59`; `fc5637f`'s module
doc moves those in `lib.rs` down by 5):

- `crates/agentspace-operator/src/main.rs:11` took `std::io::stdout().lock()` for the whole run.
- `agentspace-run`'s PassThrough tee thread (`crates/agentspace-run/src/lib.rs`, around lines
  474 to 484) writes with `std::io::stdout().write_all`.
- A `StdoutLock` is reentrant only on its own thread, so the tee thread blocked at its first write,
  and the main thread waited in `out.join()` (`lib.rs:434`) forever.

## The evidence for the cause

A program-level repro by the investigator: the debug operator in a throwaway home, with `.cmd`
stand-ins through the test seam, and a 20-second deadline.

| Stand-in for the AWS CLI during `deploy` | Result |
| --- | --- |
| Silent on stdout | Exit 1 in 1.9 s, at step 5 |
| Writes to stderr only | Exit 1 in 0.1 s, with the line passed through |
| Writes the real CLI's no-op text to stdout | Hung, killed at 20 s, with only `Deploying stack...` on stderr and stdout empty, as on the laptop |
| The same stdout shape, after the fix | Exit in 0.1 s, with the lines passed through |

**Other explanations ruled out:**

- **The AWS CLI's launcher:** a Python-free `.cmd` reproduces the hang.
- **A grandchild holding the pipes:** no line ever passed through, and no child was left.
- **Stdin or console handling:** the stdin is null, and the stderr-only shape passes.

## Why it was missed

`conformance.md`'s Coverage row had no `deploy` check (`deploy`, `sync`: None), so #0139's
statement that conformance `deploy` cases passed was mistaken. The `sync` crate's `deploy` tests
write to stdout, but they never run through `main`, so nothing held the lock.

## The fix

`main.rs` keeps an unlocked `std::io::stdout()`, and each write takes the lock for itself (commit
`4f18b59`). The later commit `fc5637f` adds comments and documentation only.

- **`conformance/operator/test-unmet-deploy-passthrough.ps1`:** 4 results. It stops at step 5 with

- **`cargo fmt --check` and `cargo clippy --all-targets -- -D warnings` are clean, and

## Other paths checked

## Findings

1. **The first run's exit code was not captured, and the second run supplied it: 0.** The first
   run's runner started the process with a redirect and held its handle only in the first call;
   the second call found it already ended and read no code. The indirect evidence (no `agentspace:`
   line, `sync` reaching the push, the stamp written) agreed with the second run's code. The test
   `deploy_passthrough.rs` also shows exit 0 and 255 on the built binary against stand-ins.
2. **The sync's first Rust run on the box worked end to end:** the CA check, the staged copy, the
   install, `CLAUDE.md`, the localswim CLI build and copy, and the push. The box's files were
   rewritten as the table of step 5 shows. **Nothing about their contents was read**, so the first
   run shows that the files were replaced and the install's closing lines printed, not that the
   content is right (the install's own checks printed their `Installed:` lines, which is its proof
   of the sshd settings).
3. **Transcript-only finding:** the first `lease list` printed lease IDs and project names into a
   subagent's transcript, because the mask had no rule for them. The rule was added, and nothing
   reached the record, the repository or a card. A future run SHOULD count the leases in the same
   command that lists them.
4. **Transcript-only finding:** a `down` wait loop read only stdout, so it ran 20 read-only
   `status` calls. `status` writes to stderr. It started no second `down`, and the box was not
   affected.
5. **The binaries carry `4f18b59`'s code, not `HEAD`'s.** `HEAD` moved to `fc5637f` during the
   first run. That commit is comments and documentation only.
6. **The operator binary is 512 bytes smaller than S01's**, consistent with the one-line change in
   `main.rs`; no other difference was looked for.
7. **The second run's redirect, through a wrapper script, hid the running `deploy`'s output until
   it ended**, while the first run's two files showed it at 20 seconds; why the two differed was
   not examined. A later live check that wants to see the lines arrive SHOULD redirect the way the
   first run did, or read the process's pipes itself, and SHOULD check a file's size while it runs.
